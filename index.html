One tool, four steps, every day

1

Look

Finds every copy of .NET on the machine — including the places Windows keeps it that most tools never check.

2

Compare

Checks each one against a policy of what’s allowed. “Too old” is a setting someone can change — not code.

3

Update

Asks Microsoft what the current version is, downloads it, confirms it’s genuine, installs it.

4

Retire

Removes the outdated version — but only once the newer one is confirmed installed and working.

What I Learned

Three lessons

  1. Scale changes engineering.
    Safety means something different at 1,600 machines than at one.
  2. A fix isn’t finished until it covers every case.
    .NET hid in five places. App versions hide in every user profile. Finding all of them was the work.
  3. Build for the next version, not this one.
    The .NET tool asks Microsoft what’s current on every run — so a new release needs nothing from me.
40 sec (trim to 30) — cut SECOND if over. Reference the stories, do NOT re-explain them. All three referents are now things the audience has actually seen.

1. Scale: 1,600 machines (slide 2) and per-user app versions (slide 7). Q&A depth if asked: Dell’s management software held locks on the exact files my .NET cleanup was deleting, so the fix was all-or-nothing removal — “at one machine that’s a bug, at 1,600 it’s an outage.”

2. ⭐ Both flagship projects were really completeness problems, and the audience just saw both: “.NET was in five different places on the machine, including one only the scanner was reading. App versions live per user, so clearing one profile left the finding open. In both cases the engineering wasn’t the fix — it was making sure I’d found everything.”

3. ⭐ Strongest note to end on — it’s the line that made the .NET slide land: “The tool asks Microsoft what the current version is every time it runs. So when a new .NET ships, nobody touches it. I tried to build things that don’t need me next quarter.” Straight into the close.
